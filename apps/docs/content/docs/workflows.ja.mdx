ワークフローは、仕事が進むステージを並べた、名前とバージョンを持つリストです。エージェントが 1 ステップを実行し、人が承認し、条件が分岐を選び、終了ステージが締めくくります。プロセスを 1 か所に一度だけ定義し、[スクワッド](/squads)のリーダーがタスクをその通りに進めます。

<Callout type="info">
ワークフローは機能フラグ `workflows_v1` の背後にあり、デフォルトでは無効です。セルフホスト環境では `FF_WORKFLOWS_V1=true` で有効にできます。無効の間は、ワークフローのページも API も表示されません。
</Callout>

ワークフロー自体は自動で動きませんし、Multica に専用の実行エンジンもありません。ワークフローを**適用**すると、スクワッドのリーダーの指示に手順書が書き込まれ、リーダーがそれに従います。ページに表示されるのはリーダーが記録した状態であり、強制ではありません。

## ステージ

| ステージ | 役割 |
|---|---|
| **エージェント** | エージェントが作業します。リーダーは `@` メンションで依頼し、返信を待ちます。 |
| **並列** | 2〜8 のエージェントが同時に作業します。リーダーはブランチごとにサブタスクを 1 つ作って担当エージェントに割り当て、すべてが Done になったらタスクを先へ進めます。 |
| **人による承認** | 1 人以上が判断します。承認者グループ、任意の差し戻し上限、任意の再確認までの時間を指定できます。 |
| **条件** | タスクのラベルから次のステージを選びます。例: `has_label("pci-scope")`。 |
| **終了** | ワークフローを終えます。 |

承認には「承認」と「却下」の 2 つの出口があります。却下は、差し戻し上限まで前のステージに戻ります。

## ワークフローを設計する

サイドバーの**ワークフロー**を開きます。オーナーと管理者は作成・編集でき、それ以外のメンバーは閲覧のみです。

- パレットからステージの種類をキャンバスにドラッグし、ハンドル間をドラッグして接続し、選択したステージを右のパネルで編集します。エージェントや人はワークスペースから選びます。
- 編集中、サーバーがワークフローを検証してすべての問題を一覧にします。問題のあるバージョンは保存できますが、適用はできません。
- 保存するたびに不変の新しいバージョンが作られます。古いバージョンを元にした保存は、他の人の変更を上書きせずに競合として拒否されます。古いバージョンは新しいバージョンとして復元できます。
- ワークフローの名前（一覧とそのページに表示）は、ワークフローのページの**名前を変更**で変えます。定義の一部ではないので新しいバージョンは作られず、キーも変わりません。

## ワークフローを別のワークスペースや環境へ移す

ワークフローはプレーンテキストです。ワークフローのページで**ダウンロード**または**コピー**を選ぶと YAML が得られます。移行先のワークスペースで、ワークフロー一覧の**YAML をインポート**（または任意のワークフローの **YAML** タブ）を選び、テキストを貼り付けるかファイルを読み込んで、**キャンバスに反映**を選びます。サーバーがテキストを読み取り、問題を行番号付きで表示します。結果は元に戻せる 1 回の変更で、保存するまで何も保存されません。

- 新しいワークフローとしてインポートする場合、テキスト中のキーがそのままキーになります。既存のワークフローにバージョンを追加するには、テキストのキーがそのワークフローのキーと一致している必要があります。
- エージェントと人はテキスト中に名前で書かれ、適用先のワークスペースで検索されます。エージェント名は完全一致が必要で、承認者は `user:<id>` と書かれ、ワークスペースごとに異なります。適用前に置き換えてください。

## ワークフローのアーカイブと削除

ワークフローのページで、オーナーと管理者は**アーカイブと削除**を使えます。**アーカイブ**すると一覧から隠れ（**アーカイブを表示**で再表示）、編集と適用ができなくなります。すでに従っているスクワッドの手順書とタスクのラベルはそのままです。**元に戻す**で取り消せます。**完全に削除**できるのはアーカイブ済みのワークフローだけで、キーの入力が必要です。すべてのバージョンと履歴が削除され、元に戻せません。スクワッドがまだ従っているワークフローは削除できません。先にそのスクワッドへ別のワークフローを適用するか、指示からそのブロックを取り除いてください。

## ワークフローをスクワッドに適用する

ワークフローのページで**スクワッドに適用**を選びます。ダイアログには、リーダーが受け取る手順書そのものと、使用するラベルが表示されます。適用すると次のことが行われます。

- スクワッドの指示の中の 2 本のマーカー行の間に手順書を書き込み、残りの文章はそのままにします。同じバージョンをもう一度適用しても何も変わりません。
- ステージが指定するエージェントと、承認者グループのメンバーをスクワッドのメンバーに追加し、見つからなかったものを知らせます。
- 承認者がリーダーを起こせない場合や、他の人専用の非公開エージェントを呼び出せない場合に警告します。Multica は、連鎖を始めたコメントの投稿者として権限を確認するため、ワークフロー内のすべてのエージェントをすべての承認者が実行できる必要があります。[エージェント](/agents)を参照してください。

適用してもラベルは作成されませんが、事前に作る必要もありません。スクワッドに割り当てられたタスクはすべてワークフローに従い、リーダーが `wf:<key>` と各ステージの `phase:<stage>` ラベルを自分で付け、ワークスペースにないものは作成します。ダイアログに一覧が表示されます。

## タスクをワークフローに通す

タスクに `wf:<key>` ラベルを付け、そのワークフローに従うスクワッドに割り当てます。リーダーはタスクの `phase:` ラベルを現在のステージに設定し、エージェントのステージは `@` メンションで依頼し、返信があればタスクを進めます。その間、タスクは常にスクワッドに割り当てられたままです。

人による承認のステージでは、リーダーは承認者にメンションして待ちます。承認者はタスクに自分の言葉で返信するだけで判断できます。ラベルも、スクワッドへのメンションも不要です。リーダーは一覧にある承認者のコメントにだけ反応します。明確な承認ならタスクを進め、明確な拒否なら理由を添えて差し戻し、それ以外なら 1 度だけ確認の質問をします。

並列ステージでは、リーダーがブランチごとにサブタスクを作り、そのブランチのエージェントに割り当てるため、全員が同時に始まります。各エージェントは自分のサブタスクを **Done** で終えなければなりません。Multica がリーダーを再び起こすのはサブタスクが Done か Cancelled になったときだけで、In Review で止まるとリーダーは待ち続けます。手順書は各サブタスクにその旨を書き込みます。最後のサブタスクが Done になると、リーダーは結果を読んでタスクを先へ進めます。サブタスクが取り消された場合や、エージェントが作業できない場合は、人が判断するまでステージは止まります。

## パイプライン

サイドバーの**パイプライン**は、1 つのワークフローのタスクをステージごとに列で表示します。スクワッドで絞り込んだり、どのスクワッドにも割り当てられていないタスクだけを表示したりできます。人による承認のステージには、誰を待っているかが表示されます。フェーズラベルがない、複数ある、どのステージにも一致しないタスクは別に一覧されるので、修正しやすくなっています。 並列ステージでは、タスクのカードに完了したブランチ数も表示され、ブランチごとの行からサブタスクを開けます。
